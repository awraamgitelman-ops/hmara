1. Проблема «Спортивного фіналу»: піки трафіку та буферизація

Специфіка онлайн-мовлення (Live Streaming) кардинально відрізняється від звичайного Video-on-Demand (VoD на зразок Netflix чи YouTube). Коли починається фінал Ліги чемпіонів або топовий кіберспортивний матч, аудиторія не накопичується поступово — від 20,000 до 800,000+ глядачів підключаються до одного й того самого потоку протягом 3–5 хвилин.

Головні інженерні виклики такої трансляції:

  • Ефект «Колеса очікування» (Rebuffering): Будь-яка затримка у віддачі 2-секундного відеочанка (HLS/CMAF fragment) викликає зупинку відтворення, що провокує шквал негативу та відтік підписників;
  • Вузьке місце оригін-сервера (Origin Overload): Якщо мільйон плеєрів одночасно запитують свіжий плейлист live.m3u8, оригін-сервер падає за секунди через вичерпання TCP-стека;
  • Висока вартість вихідного трафіку: Роздача потоку 1080p@60fps (бітрейт ~6.5 Mbps) на 500,000 глядачів генерує понад 3.25 Тбіт/с сумарної смуги, що в міжнародних публічних хмарах коштувало б десятки тисяч доларів за одну трансляцію.

2. Оригін-сервери та апаратне транскодування (GPU Transcoding)

Для прийому вхідного RTMP/SRT сигналу від студії та генерації адаптивного мультибітрейту (Adaptive Bitrate Streaming — ABR) у форматах 1080p, 720p, 480p і 360p LIKEMARK використовує виділені сервери з GPU-прискорювачами:

  • Compute & GPU: Сервери на базі процесорів AMD EPYC 7763 з картами NVIDIA RTX / L4 з підтримкою апаратного декодування та кодування NVENC 8-го покоління (HEVC/H.265 та AV1);
  • Low-Latency HLS (LL-HLS) / CMAF: Затримка між реальною подією на стадіоні та екраном користувача скорочена до 2.1 секунди завдяки фрагментації потоку на мікрочанки тривалістю 500 мс (Chunked Transfer Encoding).

3. Сховище S3 на Ceph NVMe: висока пропускна здатність запису/читання

Для архівів відео (VoD), функцій Catch-up / Time-Shift (перемотка ефіру назад) та тимчасового зберігання згенерованих сегментів розгорнуто розподілений кластер S3 Object Storage на базі Ceph Nautilus:

  • Повна сумісність з AWS S3 API;
  • 100% NVMe пули накопичувачів із трикратною реплікацією даних (3x Replication) між незалежними стійками;
  • Швидкість читання кластера перевищує 40 ГБ/с, що дозволяє миттєво віддавати запити тисячам edge-проксі одночасно.

4. Мережа доставки контенту (CDN): BGP Anycast та кешування чанків

Щоб розвантажити оригін-сервери, архітектура LIKEMARK спирається на гео-розподілену мережу Edge CDN:

  1. BGP Anycast роздача: Користувач автоматично підключається до найближчого вузла CDN (Київ, Варшава, Франкфурт або Амстердам) з пінгом менше 8–15 мс;
  2. Direct Peering з українськими провайдерами: Прямі з'єднання з UA-IX, DTEL-IX, Giganet, а також прямі BGP-стики з провідними операторами зв'язку (Kyivstar, Vodafone, Укртелеком, Lanet, Triolan);
  3. Origin Shielding (Захисний шар): Запити від десятків edge-серверів спочатку агрегуються проміжним шаром Shielding Proxies, що зводить звернення до оригін-сервера лише до 1 запиту на кожний новий фрагмент відео.

5. Протокол HTTP/3 (QUIC): ліквідація лагів на мобільному інтернеті

Понад 68% глядачів дивляться стріми зі смартфонів через мобільні мережі 4G/LTE чи Wi-Fi. Головна вада традиційного протоколу TCP — Head-of-Line Blocking: втрата навіть одного пакету змушує плеєр чекати його повторної доставки, зупиняючи відтворення всього відео.

Впровадження протоколу HTTP/3 на основі UDP (QUIC) на серверах LIKEMARK дозволило:

  • Усунути блокування черги пакетів: кожен відео- та аудіопотік передається в незалежних стрімах;
  • Підтримати 0-RTT Connection Establishment: плеєр підключається миттєво без зайвих мережевих рукостискань (handshakes);
  • Забезпечити Connection Migration: при переході користувача з домашнього Wi-Fi на 4G трансляція не переривається ні на мілісекунду.

6. Конфігурація Nginx для безшовного кешування HLS/DASH

Ось ключовий фрагмент конфігурації Edge CDN ноди LIKEMARK для обробки HLS трафіку з блокуванням паралельних запитів:

/etc/nginx/conf.d/cdn-edge-streaming.conf nginx 
proxy_cache_path /var/cache/nginx/hls_segments 
                 levels=1:2 
                 keys_zone=LIVE_SEGMENTS:256m 
                 max_size=100g 
                 inactive=120m 
                 use_temp_path=off;

server {
  listen 443 ssl http2;
  listen 443 quic reuseport; # Включення HTTP/3 (QUIC)
  server_name cdn.likemark.cloud;

  # Додавання заголовка Alt-Svc для автоматичного узгодження HTTP/3
  add_header Alt-Svc 'h3=":443"; ma=86400';

  # 1. Кешування статичних сегментів відео (.ts / .m4s / .mp4)
  location ~* \.(ts|m4s|mp4)$ {
    proxy_pass http://origin_shield_cluster;
    proxy_cache LIVE_SEGMENTS;
    proxy_cache_valid 200 206 120m;
    proxy_cache_valid 404 1s;

    # Захист оригіну: лише 1 запит іде на оригін, інші чекають у кеші
    proxy_cache_lock on;
    proxy_cache_lock_timeout 2s;
    proxy_cache_use_stale error timeout updating http_500 http_502;

    add_header X-Cache-Status $upstream_cache_status;
    proxy_ignore_headers Cache-Control Expires Set-Cookie;
  }

  # 2. Мікрокешування живих плейлистів (.m3u8 / .mpd) на 1 секунду
  location ~* \.(m3u8|mpd)$ {
    proxy_pass http://origin_shield_cluster;
    proxy_cache LIVE_SEGMENTS;
    proxy_cache_valid 200 1s;
    proxy_cache_lock on;
    proxy_cache_lock_timeout 500ms;

    add_header Cache-Control "public, max-age=1";
    add_header X-Cache-Status $upstream_cache_status;
  }
}
Чому директива proxy_cache_lock критично важлива
Коли новий 2-секундний відеофрагмент з'являється у плейлисті, 50,000 плеєрів одночасно надсилають GET-запит на цей файл. Без proxy_cache_lock on усі 50,000 запитів одномоментно проб'ють кеш і попрямують на оригін-сервер (так званий cache stampede), викликавши повний колапс оригіну.
