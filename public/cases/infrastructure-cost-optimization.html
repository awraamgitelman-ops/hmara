1. Синдром «Хмарного шоку»: куди непомітно зникають гроші

Більшість українських технологічних компаній, стартапів та e-commerce проєктів спочатку обирають великі публічні гіперскейлери (AWS, Azure, GCP), розраховуючи на гнучкість та простоту старту. Проте вже за 6–12 місяців бізнес стикається з явищем Cloud Bill Shock: щомісячні рахунки зростають у 2.5–4 рази швидше, ніж дохід компанії.

Аналіз понад 80 аудитованих інфраструктур показує стандартні джерела фінансових витоків:

  • Хронічний оверпровіжинінг (Overprovisioning): Запитані ресурси (CPU/RAM requests) у Kubernetes по замовчуванню завищені в 3–5 разів «про всяк випадок», через що середнє корисне завантаження серверів становить лише 18–25%;
  • «Забуті» ресурси (Orphaned Resources): Невидалені тестові середовища розробників (Dev/Staging), невживані томи дисків (Unattached EBS volumes), снапшоти трирічної давнини та статичні IP-адреси;
  • Плата за вихідний трафік (Egress Tax): Гіперскейлери стягують від $0.09 до $0.14 за кожен гігабайт даних, що виходить за межі їхньої мережі, включаючи API-запити та бекапи.
Парадокс хмарної економіки
Компанії часто вважають, що публічна хмара дешевша завдяки відсутності капітальних витрат (CapEx). Проте при стабільному цілодобовому навантаженні (baseline load) операційні витрати (OpEx) на оренду віртуальних ядер у гіперскейлерах перевищують вартість виділеної приватної хмари в 2.8–3.4 раза щомісяця.

2. Методологія FinOps: Інформування → Оптимізація → Контроль

FinOps (Financial Operations) — це інженерно-управлінська дисципліна, яка об'єднує розробників, інфраструктурних інженерів та фінансовий департамент навколо прозорості вартості кожного мікросервісу:

  1. Етап 1: Інформування (Inform): Впровадження інструментів деталізації витрат (OpenCost / Kubecost / Prometheus cost-metrics). Кожна команда бачить, скільки коштує розгорнутий ними мікросервіс у перерахунку на 1 активного клієнта;
  2. Етап 2: Оптимізація (Optimize): Вирівнювання лімітів, видалення зайвих інстансів, перехід на енергоефективні процесори AMD EPYC, впровадження компресії трафіку та автоматичного вимикання dev-середовищ на вихідні;
  3. Етап 3: Контроль (Operate): Автоматизовані CI/CD перевірки: якщо пул-реквест збільшує очікувані інфраструктурні витрати на 15%+, він потребує обов'язкового апруву ліда команди.

3. Оптимізація Kubernetes: Rightsizing, Requests vs Limits

Найбільш поширена помилка в Kubernetes — неправильне конфігурування resources.requests та resources.limits:

  • Якщо встановити занадто високі requests: Планувальник (kube-scheduler) вважає, що нода заповнена, і не розміщує нові поди, змушуючи кластер додавати нові дорогі вузли (node autoscaling), хоча реальний CPU тримається на рівні 15%;
  • Якщо встановити занадто жорсткі CPU limits: Linux-ядро задіює механізм CFS Quota Throttling, штучно сповільнюючи виконання коду та викликаючи 504 таймаути;
  • Рішення LIKEMARK: Поєднання Vertical Pod Autoscaler (VPA) в режимі recommendations з Horizontal Pod Autoscaler (HPA) по користувацьких метриках (RPS та черга повідомлень RabbitMQ/Kafka, а не тільки сирий CPU).

5. Приклад конфігурації: HPA + VPA та ResourceQuota у K8s

Зразок продакшн-маніфесту LIKEMARK для безпечного автоскейлінгу мікросервісу без переплат:

k8s-production-finops.yaml yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-service-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-service
  minReplicas: 2
  maxReplicas: 16
  metrics:
  # Пріоритетна бізнес-метрика: кількість запитів на секунду (RPS)
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "450"
  # Допоміжна метрика CPU з порогом 75%
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 75
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300 # Плавний спад, щоб уникнути флеппінгу
      policies:
      - type: Percent
        value: 20
        periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0   # Миттєва реакція на сплеск
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15

7. 7-кроковий чек-лист експрес-аудиту IT-витрат

  1. Зробіть ревізію Dev/Staging середовищ: Налаштуйте автоматичну зупинку неробочих інстансів з 20:00 до 08:00 у будні та повне вимкнення на вихідні (економія до 60% на тестових серверах);
  2. Перевірте співвідношення Requests до реального використання: Якщо середній CPU pod становить менше 30% від request, зменшуйте запит на 40%;
  3. Приберіть CPU limits там, де це можливо: Залишайте тільки Memory Limits для запобігання OOMKilled, а для CPU дозволяйте burst-споживання в межах ноди;
  4. Очистіть непідключені диски та снапшоти: Запустіть скрипт пошуку status: available дисків і видаліть старі копії;
  5. Переведіть статичний контент на Edge CDN: Розвантажте додатки від роздачі картинок та відео;
  6. Відмовтеся від погодинних віртуалок під baseline-навантаження: Постійне навантаження повинно жити на виділеному залокованому залізі або приватній хмарі;
  7. Замовте незалежний аудит: Свіжий погляд сертифікованих інженерів LIKEMARK дозволяє знайти оптимізаційні резерви вже протягом перших 48 годин перевірки.
