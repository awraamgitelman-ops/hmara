Disaster Recovery (DRaaS)

1. Чому резервних копій (Backup) більше недостатньо

Більшість українських підприємств вважають, що наявність щоденного бекапу бази даних о 02:00 на зовнішній диск гарантує безпеку. Проте за реальної аварії — фізичного руйнування майданчика, знеструмлення мережевого вузла, шифрувальника-вимагача (Ransomware) або фатального збою СГД — традиційне відновлення з бекапу перетворюється на катастрофу:

  • Втрата робочого дня даних: Якщо аварія сталася о 16:30, усі замовлення, проводки 1С та платежі за попередні 14 годин втрачено безповоротно;
  • Час розгортання резерву (RTO): Завантаження 4 ТБ бекапу по мережі, розгортання нових серверів, встановлення ОС та перевірка цілісності займає від 12 до 36 годин, протягом яких бізнес повністю паралізовано;
  • Пошкоджені бекапи: До 38% компаній під час справжньої кризи дізнаються, що їхні резервні копії або містили помилки цілісності, або також були зашифровані зловмисниками.
Різниця між Backup та Disaster Recovery (DRaaS)
Backup відповідає на питання: «Чи збережені файли?». Disaster Recovery відповідає на питання: «Як швидко бізнес відновить операційну діяльність після повної втрати основного дата-центру?». DRaaS забезпечує готову гарячу репліку всієї інфраструктури, яка вмикається в роботу автоматично.

2. Метрики RTO та RPO: як визначити допустимі втрати бізнесу

Побудова правильної відмовостійкої стратегії базується на двох ключових інженерно-економічних параметрах:

  1. RTO (Recovery Time Objective): Максимально допустимий час, за який інфраструктура має повністю відновити роботу після оголошення аварії. Для критичних систем мета — менше 5 хвилин;
  2. RPO (Recovery Point Objective): Максимальний проміжок часу, за який дані можуть бути втрачені. Для транзакційних систем інженери LIKEMARK налаштовують конфігурацію, яка забезпечує RPO < 15 секунд завдяки безперервній асинхронній реплікації журналів (WAL / Binlog / Storage snapshots).

3. Топологія LIKEMARK DRaaS: Active-Active та Active-Standby

Інфраструктура клієнта розгортається у двох географічно ізольованих локаціях:

  • Primary Site (Основний сайт): Дата-центр Tier III у Варшаві (Equinix WA1/WA2), з прямим оптичним каналом до України;
  • DR Secondary Site (Резервний сайт): Дата-центр Tier III у Франкфурті (Interxion / Digital Realty), віддалений на 1,000+ км для захисту від регіональних катаклізмів;
  • Dedicated L2 Metro-Transport: Виділений захищений канал L2 (QinQ) пропускною здатністю 40 Gbps з круговою затримкою (RTT) 14.8 мс між майданчиками.

4. Технології безперервної реплікації даних на рівні блоків та БД

Для усунення ризику втрати даних LIKEMARK використовує комбіновану багаторівневу модель реплікації:

  • Storage-Level Block Replication (Ceph RBD Mirroring): Блочні пристрої віртуальних машин та контейнерних томів реплікуються в асинхронному режимі з підтримкою дедуплікації та компресії zstd, що мінімізує навантаження на канал зв'язку;
  • Database Streaming Replication: PostgreSQL patroni-кластер або MySQL Group Replication із синхронним підтвердженням для фінансових записів та асинхронними репліками у Франкфурті;
  • Veeam Cloud Connect CDP: Безперервний захист даних для корпоративних систем на базі Windows Server / Hyper-V / VMware із можливістю відкату на будь-яку секунду за останні 72 години (Granular Point-in-Time Recovery).

5. Автоматичний Failover: перемикання трафіку через BGP Anycast

Найскладніший етап відновлення — перенаправлення клієнтів на резервний майданчик без ручної зміни DNS-записів (адже DNS TTL у багатьох інтернет-провайдерів може оновлюватися годинами).

Інженери LIKEMARK налаштовують BGP Anycast Routing: обидва дата-центри анонсують одну й ту саму IP-підмережу через протокол BGP. У разі аварії системи автоматичного моніторингу закривають сесію анонсування на основному сайті, і світові Tier 1 маршрутизатори протягом 15–30 секунд направляють весь трафік на резервний сайт у Франкфурті.

/etc/keepalived/healthcheck.sh bash 
#!/usr/bin/env bash
# Automated Healthcheck & Failover Trigger (BGP / Patroni cluster)
PRIMARY_TARGET="https://lb-pl.likemark.internal/healthz"
FAIL_COUNT_FILE="/tmp/dr_fail_count"
MAX_FAILS=3

HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" --connect-timeout 2 --max-time 3 "$PRIMARY_TARGET")

if [ "$HTTP_CODE" -ne 200 ]; then
  CURRENT_FAILS=$(cat "$FAIL_COUNT_FILE" 2>/dev/null || echo 0)
  CURRENT_FAILS=$((CURRENT_FAILS + 1))
  echo "$CURRENT_FAILS" > "$FAIL_COUNT_FILE"

  if [ "$CURRENT_FAILS" -ge "$MAX_FAILS" ]; then
    echo "[CRITICAL] Primary site healthcheck failed $MAX_FAILS times. Initiating DR Failover!"
    # 1. Withdraw BGP Anycast routes from Warsaw routers
    vtysh -c "configure terminal" -c "router bgp 65001" -c "no network 194.36.176.0/24"
    
    # 2. Promote Standby Database cluster in Frankfurt to Primary
    /usr/local/bin/patroni_ctl -c /etc/patroni/frankfurt.yml failover --candidate node-dr-de-01 --force
    
    # 3. Start standby compute services in Frankfurt
    systemctl restart keepalived
    
    # 4. Notify on-call DevOps via Telegram
    /usr/local/bin/notify-telegram.sh "[ALERT] DR Failover to Frankfurt Activated Successfully!"
  fi
else
  # Reset fail count on healthy check
  rm -f "$FAIL_COUNT_FILE"
fi

7. Чек-лист для CTO: 6 кроків до створення надійного DR-плану

  • Проведіть BIA (Business Impact Analysis): Визначте системи Tier 0 (платежі, CRM, логістика, без яких бізнес зупиняється) та другорядні системи;
  • Зафіксуйте цільові RTO / RPO: Затвердьте з фінансовим директором допустимі втрати в годинах та гривнях;
  • Розділіть майданчики географічно: Відстань між основним та резервним ЦОД має становити не менше 300 км для захисту від масштабних катаклізмів;
  • Забезпечте захист бекапів від шифрувальників (Immutable Backups): Резервні копії мають зберігатися в режимі WORM (Write Once, Read Many) без можливості видалення;
  • Тестуйте відновлення регулярно: План аварійного відновлення, який не перевірявся на практиці хоча б раз на 6 місяців, вважається неробочим;
  • Підпишіть SLA з постачальником хмари: Переконайтеся, що відповідальність за доступність майданчика закріплена фінансовими гарантіями в договорі.
